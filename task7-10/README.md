# Задание 7. Проектирование схем коллекций для шардирования данных

## Схемы коллекций

### Коллекция `orders`

```json
{
  _id: ObjectId,
  user_id: ObjectId,
  created_at: DateTime,
  items: [ { product_id: ObjectId, qty: Int, price: Decimal } ],
  status: String,
  total: Decimal,
  geo_zone: String
}
```

Индексы:

* `{ _id_: 1 }` - уникальный
* `{ user_id: 1, created_at: -1 }` - для быстрого поиска истории пользователя по убыванию даты
* `{ status: 1 }` - для мониторинга/очередей обработки

### Коллекция `products`

```json
{
  _id: ObjectId,
  name: String,
  category: String,
  price: Decimal,
  stock: {
    "geo_zone": Int
  },
  attributes: { "attribute": String, ... }
}
```

Индексы:

* `{ _id_: 1 }` - уникальный
* `{ category: 1, price: 1 }` - для поиска по категории и фильтрации по диапазону цен
* `{ "stock.$**": 1 }` - для быстрого поиска остатков по геозоне

### Коллекция `carts`

```json
{
  _id: ObjectId,
  cart_id: ObjectId,
  owner_id: ObjectId | null,
  items: [ { product_id: ObjectId, quantity: Int } ],
  status: String,
  created_at: DateTime,
  updated_at: DateTime,
  expires_at: DateTime
}
```

Индексы:

* `{ _id_: 1 }` - уникальный
* `{ owner_id: 1, status: 1 }` - быстрый поиск текущей корзины
* TTL индекс `{ expires_at: 1 }` с `expireAfterSeconds: 0` для автоматической очистки

## Выбор шард-ключей и стратегия шардирования

### Коллекция `orders`

**Шард-ключ:** `{ user_id: "hashed" }`.

**Причины:**

* Основной способ поиска истории заказов - по `user_id`. При запросе (find({ user_id: X })) MongoDB с hashed shard key целевой запрос попадает к одному конкретному шарду, где хранятся все документы с тем же `user_id`
* Hashed обеспечивает хорошее распределение пользователей между шардами, избегая концентрации вставок на одном шарде
* Большинство операций вставки (создание заказа) будут равномерно распределены

**Команды MongoDB (пример):**

```js
sh.enableSharding("mobilemir_db");
db.orders.createIndex({ user_id: 1 });
sh.shardCollection("mobilemir_db.orders", { "user_id": "hashed" });
```

**Дополнительно - geo_zone**

Была идея добавить геошардирование, но, так как пользователи могут делать заказы в разных геозонах, и в этом случае история заказов одного пользователя распределялась бы по нескольким шардам. Это замедляет запросы и увеличивает нагрузку, так как MongoDB придётся делать scatter-gather по всем шардам. Кроме того, популярные геозоны создают «горячие» шарды, а редкие - пустые, что ухудшает балансировку. Поскольку основные операции ориентированы на пользователя (поиск активной корзины, история заказов, отображение статуса), шардирование по user_id обеспечивает более быстрый и равномерный доступ к данным. Фильтрация по геозоне остаётся важной, но её можно эффективно реализовать через обычные индексы, без использования шард-ключа.

### Коллекция `products`

**Шард-ключ:** `{ category: 1, _id_: "hashed" }` (комбинация: range по category, hashed по _id как суффикс).

**Причины:**

* Поиск на странице каталога часто фильтруется по `category` и по диапазону `price`. Наличие категории в префиксе позволяет выполнять range-запросы по ценам в пределах категории (chunk'и сгруппированы по категориям)
* `_id` (hashed) внутри категории равномерно распределяет документы между шардами, предотвращая перегрузку при большом количестве товаров в популярных категориях
* Обновления остатков (`stock`) - чаще происходят по конкретному `_id`, то есть обновление будет локализовано в конкретном документе равномерное распределение уменьшает концентрацию обновлений

**Команды MongoDB (пример):**

```js
db.products.createIndex({ category: 1, price: 1 });
sh.shardCollection("mobilemir_db.products", { "category": 1, "_id": "hashed" });
```

### Коллекция `carts`

**Шард-ключ:** `{ owner_id: "hashed" }`

**Причины:**

* Частые операции поиска - `find({ owner_id: "ID", status: "active" })`
* Высокая кардинальность поля `owner_id` (много уникальных сессий/пользователей) - хорошее распределение.
* Слияние гостевой корзины: при логине приложение читает guest cart по `owner_id`, затем переносит items в `owner_id`(user_id) и отмечает guest как abandoned. Перенос подразумевает update/insert, вероятная операция перемещения между шардами - это нормальная операция, не частая для одной корзины (один раз при логине)
* `expires_at` TTL индекс обеспечивает автоматическую очистку старых корзин, не зависящую от шардинга

**Команды MongoDB (пример):**

```js
db.carts.createIndex({ owner_id: 1, status: 1 });
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });
sh.shardCollection("mobilemir_db.carts", { "owner_id": "hashed" });
```

# Задание 8. Выявление и устранение «горячих» шардов

## Метрики для отслеживания состояния шардов

#### 1. Нагрузка на CPU и память каждого шарда

Пример:
```
db.serverStatus().mem   // информация по памяти
db.serverStatus().extra_info    // включает использование CPU
```
Для мониторинга CPU и памяти на уровне ОС лучше использовать внешние инструменты типа top, htop или интеграции с Prometheus

#### 2. Нагрузка по операциям ввода/вывода, время отклика

Позволяют увидеть распределение операций по шардам

Пример:
```
db.serverStatus().opcounters    // количество операций (insert, query, update, delete)
db.serverStatus().metrics.operationLatency  // время выполнения операций (если включено профилирование)
```

#### 3. Размер данных и чанков на каждом шарде

Накопление слишком больших чанков указывает на дисбаланс

Пример:
```
sh.status()     // общее состояние шарда и распределение чанков
db.collection.getShardDistribution()    // вывод распределения данных по шардам и чанкам
```

#### 4. Нагрузка по ключам шардирования

Логирование для выявления горячих ключей (например, через профилирование или анализ логов)

Пример:
```
db.setProfilingLevel(1, { slowMs: 100 })    // включение профилирования медленных запросов
db.system.profile.find({ "command.shardKey": { $exists: true } }).pretty()      // анализ запросов по ключам
```


## Механизмы автоматического перераспределения данных

#### 1. Автоматический раздел чанков (auto-split) и перемещение чанков (balancer)

Включить balancer для распределения чанков между шардами.

Пример:

```
sh.setBalancerState(true)   // Включить балансировку
sh.setAutoSplit(true)   // Включить автоматический сплит чанков
```

#### 2. Изменение шард-ключа на составной с хешированием популярного поля

Как было сделано в предыдущем задании: `{ category: 1, _id: "hashed" }`.

Это разгружает популярные категории по значениям _id.

#### 3. Ручное дробление чанков горячих ключей

Позволяет более тонко разбить горячий диапазон по _id.

Пример:

```
sh.splitAt("mobilemir_db.products", { category: "Электроника", _id: ObjectId("...") })
```

#### 4. Перераспределение чанков с помощью команды

Перемещать чанки с горячими значениями на менее загруженные шарды.

Пример:

```
sh.moveChunk("mobilemir_db.products", { category: "Электроника", _id: ObjectId("...") }, "shard002")
```

# Задание 9. Настройка чтения с реплик и консистентность

### Таблица с операциями чтения и указанием, должны ли они идти на primary или secondary

| Операция чтения                                             | Коллекция | Чтение с Primary | Чтение с Secondary | Обоснование и требования к консистентности                                                       |
| ----------------------------------------------------------- | --------- | ---------------- | ------------------ | ------------------------------------------------------------------------------------------------ |
| Запросы на поиск и просмотр товаров                         | products  | Нет              | Да                 | Обновления товаров редкие, допускается небольшая устарелость данных, высокая нагрузка на чтение. |
| Проверка наличия товара перед покупкой (актуальный остаток) | products  | Да               | Нет                | Требуется консистентность, избегать продажи отсутствующих товаров.                               |
| Просмотр списка заказов пользователя                        | orders    | Нет              | Да                 | Приемлема устарелость, для быстрой загрузки истории заказов.                                     |
| Проверка статуса конкретного заказа                         | orders    | Да               | Нет                | Важно показать актуальный статус, например, для оплаты или доставки.                             |
| Просмотр содержимого корзины                                | carts     | Нет              | Да                 | Допускается небольшое отставание статусов, высокая нагрузка чтения.                              |

### Описание допустимой задержки репликации

- Обычно задержка составляет от 0.5 до 2 секунд.
- Для операций, где необходима сильная консистентность (проверка остатков, обновление заказа) нельзя читать с Secondary, либо применять стратегию Read Concern "linearizable" или "majority" на Primary.
- Для операций с допустимой устарелостью (просмотр каталогов, истории) можно читать с Secondary с задержкой до 2 секунд, чтобы разгрузить Primary.

### Обоснование выбора

- Частота обновлений товара обычно низкая, поэтому чтение с Secondary для просмотра рационально и ускоряет отклик.
- Критичная бизнес-логика (продажа, статус заказа) требует строгой консистентности, поэтому чтение строго с Primary.
- Задержка репликации вполне приемлема для Secondary, но при необходимости быстрого отражения изменений используются Primary или более строгие уровни Read Concern.

## Задание 10.2 Концептуальная модель и ключи

| Сущность                                | Partition Key | Clustering Key  | Обоснование                                                                                                                                                                         |
| --------------------------------------- | ------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Пользовательские сессии (user_sessions) | session_id    | -               | session_id гарантирует равномерное распределение сессий по всем узлам кластера и все операции чтения/записи идут по конкретному session_id + не нужны сложные запросы по диапазонам |
| Корзины (carts)                         | owner_id      | updated_at DESC | Partition key для легкого доступа к сессии пользователя, кластеризация по времени обновления для эффективного доступа к последнему состоянию корзины                                |

Пример создания таблицы `orders`:


```sql
CREATE TABLE user_sessions (
    session_id UUID,
    user_id UUID,
    created_at TIMESTAMP,
    last_activity_at TIMESTAMP,
    ended_at TIMESTAMP,
    user_agent TEXT,
    ip_address INET,
    geo_zone TEXT,
    session_data MAP<TEXT, TEXT>,
    PRIMARY KEY ((session_id))
) WITH default_time_to_live = 2592000;

CREATE INDEX ON user_sessions (user_id);
```

Пример создания таблицы `carts`:

```sql
CREATE TABLE carts (
    owner_id UUID,
    updated_at TIMESTAMP,
    cart_id UUID,
    items MAP<UUID, INT>,
    status TEXT,
    created_at TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY ((owner_id), updated_at, cart_id)
) WITH CLUSTERING ORDER BY (updated_at DESC);
```
